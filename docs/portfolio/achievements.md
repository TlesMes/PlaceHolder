# PlaceHolder — 성과 정리

> 이력서·포트폴리오 작성용 재료. 각 항목은 **도메인 → 문제 → 해결 → 결과** 구조로 정리했다.
> 수치는 전부 저장소에 근거 문서가 있다(각 항목 하단 링크).

## 핵심 성과 — 측정으로 병목을 규명하고 구조를 바꿔 처리량 3.6배

네 항목이 하나의 흐름이다. **결함 발견(A) → 락으로 차단(A) → 측정으로 병목 규명(C) →
구조 변경으로 원인 제거(B) → 남은 격차 추적(D)** 순서로 이어진다.
지면이 넉넉하면 이어서, 좁으면 **B 단독**으로 쓴다.

### A. 정산 적립 유실(lost update) 차단

- **도메인** 여러 예약자가 **같은 제공자의 서로 다른 좌석**을 동시 구매 — 인기 이벤트의 정상 트래픽 형태
- **문제** 좌석 확정 경로가 제공자 계정 잔액을 **락도 버전도 없이 read-modify-write**.
  좌석 락·예약자 계정 락은 **다른 행**이라 이 갱신을 직렬화하지 못한다.
  기존 동시성 테스트는 *같은 좌석* 경합만 다뤄 이 축이 비어 있었다
- **해결** 재현 테스트를 먼저 작성(서로 다른 예약자 × 같은 제공자 × 다른 좌석, 10건 동시 확정) →
  비관적 락 추가, 락 순서 규약 확장(좌석 → 예약자 계정 → 제공자 계정)
- **결과** 수정 전 **거래 이력은 10행인데 잔액은 5,000**(50,000이어야 함) = **10건 중 9건 유실**,
  3회 반복 전부 재현 → 수정 후 전량 반영

> **진단이 다음 단계로 이어진다:** 이력은 INSERT라 덮어쓸 게 없고 잔액은 UPDATE라 덮어써진다 —
> 같은 사실을 두 곳에 저장하는데 갱신 방식이 달라 갈라진 것이다.

<sub>근거: PR #28 · `ProviderSettlementConcurrencyTest`</sub>

### B. 정산 잔액을 컬럼 대신 거래 이력 합계로 계산 → 처리량 3.6배

- **도메인** 좌석 확정 시 제공자에게 판매 대금 적립
- **문제** A에서 추가한 락 때문에 **같은 제공자의 판매가 계정 행 하나에서 직렬화**된다.
  인기 이벤트에서 제공자당 약 **85건/초**가 상한
- **해결** 잔액 컬럼을 **제거**하고 조회 시 거래 이력(`SETTLE`) 합계로 파생.
  커버링 인덱스 `(user_id, type, created_at, amount)` 추가
- **결과** 처리량 **85 → 304건/초 (3.6배)**, 지연 **p50 347 → 92ms**, p95 478 → 142ms, p99 496 → 165ms.
  요구 기준선(100건/초)의 3배.
  **직렬화 제거는 측정이 아니라 구조가 보증한다 — 잠글 컬럼이 존재하지 않는다.**
  같은 이유로 lost update도 구조적으로 불가능해졌다(덮어쓸 대상 자체가 없음)

<sub>근거: PR #32 · ADR-021 · `docs/performance/provider-settlement-throughput.md`</sub>

### C. 병목 원인 규명 (B의 선행 측정)

- **도메인** 정산 적립 경로 성능 진단
- **문제** 락으로 인한 직렬화 **상한이 존재한다 ≠ 그것이 병목이다.** 재설계 전에 판정이 필요했다.
  부하생성기를 분리할 수 없는 1인 환경이라 절대 처리량은 신뢰할 수 없음
- **해결** 제공자 수(1/2/4/8)를 **대조 변수**로 두어 두 실험군이 같은 환경 오염을 공유하게 만들고,
  락 보유 시간을 계측해 **`1/락보유시간`으로 이론 상한을 유도**한 뒤 실측과 대조
- **결과** 이론 상한 **91·83건/초** vs 실측 **88.1·81.2건/초** — **오차 4% 내 일치**로 원인 귀속.
  지연의 **93%가 락 대기**이고 제공자 수를 늘리면 줄어드는 것은 대기뿐(303 → 27ms)

> **측정이 재설계의 방향도 바꿨다.** "락만 제거" 비교군은 1.2~1.4배에 그쳤다 —
> 잠금 조회를 없애도 잔액 UPDATE가 커밋 시점에 같은 행을 다시 잠그기 때문이다.
> 재설계 대상이 *잠금 조회*에서 **그 행에 대한 쓰기**로 바뀌었고, 그래서 B가 컬럼 제거가 됐다.

<sub>근거: PR #31 · `docs/performance/provider-settlement-throughput.md` 7절</sub>

### D. 좌석 상태 변경 쿼리 최적화 (+21%)

- **도메인** 좌석 홀드·확정·반환·만료가 모두 지나가는 상태 변경 경로
- **문제** B 이후에도 설명되지 않는 격차가 남았다. 추적해보니 **3개 필드만 바꾸는데 6개 컬럼을 UPDATE**하고
  있었고(Hibernate 기본 동작), 그중 두 컬럼이 유니크 인덱스 `(event_id, label)`를 이뤄
  **같은 이벤트의 좌석들이 인덱스 한 자리에 집중**되고 있었다
- **해결** `@DynamicUpdate`로 변경된 컬럼만 UPDATE (인덱스는 도메인 규칙이라 유지)
- **결과** 처리량 **266 → 323건/초 (+21%)**, 이벤트 간 격차 1.47 → 1.25배

> **코드만 읽어서는 찾을 수 없는 종류다.** 애플리케이션 코드에는 `seat.confirm()`뿐이고 3필드만 바꾼다.
> 6개 컬럼을 쓴다는 건 프레임워크가 만드는 SQL이라 **실제 쿼리를 찍어봐야 보인다.**
> 원인 분리도 DB를 뒤지기 전에 **측정 픽스처를 고치는 것**에서 나왔다(제공자 수와 이벤트 수가
> 붙어 움직이고 있었음): (제공자1,이벤트1) 266 / (1,8) 392 / (8,8) 392 → **원인은 제공자가 아니라 이벤트**

<sub>근거: PR #33 · `docs/performance/provider-settlement-throughput.md` 9절</sub>

## 서브 성과

### 1. 목록 조회 통계 쿼리 설계 (fetch join 기각)

- **도메인** 이벤트 목록에 잔여/총 좌석 수 표시
- **문제** 이벤트마다 좌석 수를 개별 질의해 쿼리가 `1+2N`으로 증가.
  데이터 20배 증가 시 **p95가 15배로 선형 폭발**
- **해결** 표준 패턴인 fetch join을 **기각**하고 `GROUP BY` 집계 채택 —
  fetch join은 개수를 세려고 좌석 5만 행을 앱 메모리에 적재하고,
  `Event.seats` 양방향 매핑이 필요해 단방향 설계 원칙과 충돌한다
- **결과** 쿼리 **201 → 2건**(이벤트 수와 무관한 상수), **p95 357 → 35.65ms**,
  처리량 **21.9 → 250.8/s**. 데이터가 늘어도 응답 시간 평탄

<sub>근거: PR #6 · ADR-011</sub>

### 2. 커넥션 풀 병목 가설 검증 → 튜닝하지 않기로 결정

- **도메인** 좌석 홀드 API 부하 측정
- **문제** "커넥션 풀이 병목"이라는 가설로 튜닝을 검토. 측정 없이 늘리면 근거 없는 설정 변경이 된다
- **해결** 풀 5/10/20에서 한계 도착률(성공 p99가 1초를 넘는 지점)을 각각 측정하고 **CPU 사용률을 함께** 관측
- **결과** 한계 도착률 **390 → 840 → 890/s**. 5→10은 **2.2배**인데 10→20은 **1.06배**.
  풀 5는 **CPU가 65%로 놀면서도** 꺾임 = 연결 부족, 풀 10부터는 CPU가 한계 →
  **적정 풀 ≈ 10, 튜닝 불필요** 결론

> 측정이 가설을 3번 교정했다(풀이 병목 → 아니다 → 10 미만에선 맞다).
> 확인하지 못한 것도 문서에 남겼다 — 부하생성기가 요청을 버려 서버를 한계까지 밀지 못했으므로
> 과부하 구간의 거동은 이 측정으로 말할 수 없다.

<sub>근거: PR #7 · `loadtest/HANDOFF-D2.md`</sub>

### 3. 결제 정합성 삼중화

- **도메인** 현금 → 포인트 충전 (토스페이먼츠 연동)
- **문제** 동기 승인만으로는 **응답 유실 시 결제됐는데 포인트 미적립**.
  웹훅만으로는 즉시 반영이 안 되고, **둘 다 실패하면 시스템이 영영 인지하지 못한다**
- **해결** 동기 승인 + 웹훅 + 주기 대사 **삼중화**, 세 경로를 **동일 멱등 코어**로 수렴
  (주문 행 비관적 락 + 상태 검사). 웹훅은 페이로드를 신뢰하지 않고 결제사에 **재조회**해 검증
- **결과** 세 경로가 **동시에 도착해도 적립 정확히 1회**(반복 테스트). 금액 위변조 거부,
  알려진 미복구 경로 없음. **실제 결제사 연동으로 E2E 관통 확인**

<sub>근거: PR #22·#24·#25 · ADR-018</sub>

### 4. 결제 취소 보상 트랜잭션

- **도메인** 결제 취소·환불
- **문제** 결제는 외부 성공 + 내부 실패를 재시도로 수렴시킬 수 있지만, 취소는
  **"돈은 돌려줬는데 포인트 회수 실패"가 곧 순손실**이다.
  외부 호출을 트랜잭션에 넣으면 네트워크 시간만큼 DB 락을 점유한다
- **해결** 순서를 뒤집는다 — 되돌릴 수 있는 **DB를 먼저 커밋** → **트랜잭션 밖**에서 결제사 취소 호출 →
  성공 시 확정 기록, 실패 시 롤백.
  상태 전이를 외부 호출보다 먼저 커밋하는 것이 **동시 취소에 대한 방어선**이다
- **결과** **동시 취소 2건에도 실제 환불 1회**.
  실 결제 E2E에서 두 시각이 **1.3초 차**로 벌어져 설계한 순서대로 동작함을 관측

<sub>근거: PR #26 · ADR-019</sub>

### 5. 장애 크래시 창 자동 복구 (역방향 대사)

- **도메인** 결제 취소 도중 서버 장애
- **문제** 포인트 회수는 커밋됐는데 결제사 취소 호출 전에 죽으면 **포인트만 회수되고 현금은 미환불**.
  게다가 화면에는 이미 환불 거래가 찍혀 **"환불됐다"고 거짓말**을 한다
- **해결** 두 시각(`canceled_at` / `cancel_confirmed_at`)을 **비교**해 후보 탐지
  (`IS NULL` 조건은 부분취소 2회차 크래시를 놓친다), 결제사에 잔액을 물어 **차액만** 재취소.
  화면에서 "환불 처리 중"과 "환불 완료"를 분리
- **결과** **실 결제로 크래시 창을 재현** → 5분 뒤 배치가 자동 발화해 실제 취소 전송,
  **결제사 측 기록으로 확인**. 이중 환불·헛 적립 0건

<sub>근거: PR #30 · ADR-019</sub>

### 6. 좌석 동시 점유 락 전략 선택

- **도메인** 같은 좌석에 동시 예약 요청
- **문제** 동시 요청 시 좌석 중복 점유. 락 전략 3가지(비관적/낙관적/DB 유니크 제약) 중 선택 필요
- **해결** **이 서비스의 경합 패턴**(인기 좌석 1개에 다수 집중)을 기준으로 비교 —
  낙관적 락은 이 패턴에서 대부분의 요청이 충돌·재시도로 귀결돼 **라이브락 위험**이 가장 크고,
  유니크 제약은 홀드를 별도 테이블로 되돌려야 해 기존 설계와 충돌 → **비관적 락 채택**
- **결과** 동시 N건 요청에서 **1명만 성공**.
  만료 vs 확정 경쟁 **5종 시나리오에서 정합성 위반 0건**

<sub>근거: PR #1~4 · ADR-008</sub>

### 7. 대기열 입장 제어 원자화

- **도메인** 인기 이벤트 오픈 순간의 트래픽 유입
- **문제** 입장 판정이 **check-then-act**(활성 수 확인 → 순번 추출 → 토큰 발급)라
  동시 호출 시 상한 초과·중복 입장이 가능하다
- **해결** 세 단계를 **Redis Lua 스크립트 1회 실행으로 원자화**.
  활성 수는 HELD 좌석이 아니라 **유효 입장 토큰 수로 센다**
  (토큰만 받고 아직 홀드 전인 요청이 누락되면 한 틱에 과다 입장한다)
- **결과** **락 없이 상호배제** 확보. 여러 인스턴스·스레드가 동시 호출해도 **상한 초과 불가** —
  앱 프로세스를 늘려도 성질이 유지되는 구조

<sub>근거: PR #13·#14 · ADR-013</sub>

### 8. 대기열 이벤트 간 기아(starvation) 방지

- **도메인** 여러 이벤트가 동시에 대기열을 운영하는 상황
- **문제** 선착순 순회 방식이라 **대기자가 많은 이벤트가 틱 예산을 독식** → 소형 이벤트는 입장 0명
- **해결** DRR(Deficit Round Robin) — 예산 균등 분할 + 정수화 끝수를 이월 장부로 넘김 +
  짧은 큐의 잉여는 장부 차감 없이 재분배.
  **대기 인원 비례 배분은 의도적으로 기각** — 같은 순번의 소형 이벤트 대기자가
  수백 배 기다리게 되어 독식을 정당화하는 구조가 된다
- **결과** **33틱 실시간 실측**(rate 4, 핫 이벤트 200명 vs 소형 15명×2):
  **기아 0회**, 소진 후 전량 회수, 틱당 캡 준수, **처리량 손실 없음**

<sub>근거: PR #20 · ADR-017</sub>

### 9. 외부 API 장애 격리

- **도메인** 결제사 API 호출
- **문제** 응답 없는 서버에 대해 **요청 스레드가 무한 점유**되어 하류 지연이
  좌석 홀드 등 무관한 경로로 전파된다. **대기열로는 막을 수 없는 장애 유형**(대기열은 유입 셰이핑)
- **해결** connect 3s / read 5s 타임아웃 적용.
  그 과정에서 읽기 타임아웃이 소켓 상한이 아니라 **진행 중 요청 취소**로 구현돼 있어
  `CancellationException`이 예외 번역을 그대로 통과하는 것을 발견 →
  예외 처리를 "번역할 예외 열거"에서 **"이 계층 밖으로는 도메인 예외만 나간다"** 로 전환
- **결과** CI 부하에서만 재현되던 결함 수정(**상한 1ms에서 19/20 발현**, 30ms 이상에서 0/20).
  응답 없는 소켓 서버로 발동 검증

<sub>근거: PR #22·#26 · ADR-018</sub>

### 10. 포인트 재원 환전 구멍 차단

- **도메인** 포인트 충전(쿠폰/현금)과 결제 취소
- **문제** 잔액이 **단일 정수**라 `쿠폰 충전 → 좌석 소진 → 현금 결제 취소` 순서로
  **쿠폰이 현금으로 환전**되는 구멍. **설계 문서 self-review 중 발견**(테스트는 전부 통과 중이었다)
- **해결** EVENT/FREE/PAID **3계층 분리**. 소모는 EVENT→FREE→PAID, 환불은 PAID에서만 —
  **소모 순서가 양끝을 막는다**(이벤트분을 나중에 쓰면 사용자가 만료로 손해,
  유료분을 먼저 쓰면 서비스가 환불 재원을 잃는다)
- **결과** **구멍 재현 테스트를 먼저 실패시켜 존재를 증명한 뒤** 수정.
  실 결제 E2E로 계층 관통 확인(`DEDUCT: free 3,000 + paid 2,000`, `REFUND: paid 8,000`)

## 작성 시 참고

- **정량 수치가 확실한 항목:** 핵심 B·C·D, 서브 1·2·8·9
  나머지는 "무엇을 보장하는가"로 쓰는 항목이다.
- **핵심 A~D는 이어 쓸 때 가장 강하다.** 락으로 막은 문제를 나중에 구조로 없앤 흐름이라,
  "문제 해결 → 더 나은 해결"로 읽힌다. 좁은 지면에서는 B 단독으로도 성립한다.
- **대기열(서브 7·8)을 쓸 때:** 실제 트래픽으로 필요성을 입증한 것은 아니다.
  다만 커넥션 풀 고갈은 알려진 실패 모드이고 실측 불가는 1인 환경 제약이므로,
  **"알려진 실패 모드에 대한 예방 설계"** 로 쓰고, 미확보 부분은
  *기능 타당성*이 아니라 **파라미터 근거**(입장 상한·rate가 추정값)로 좁혀 적는다.
- **재현 테스트 선행(음성 대조군)** 은 별도 항목으로 두지 않고
  핵심 A와 서브 10에 *"고치기 전에 재현부터 했다"* 는 한 줄로 녹인다.
