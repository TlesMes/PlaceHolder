# ADR-015. 대기열 이탈 유저 세션 회수 — 이탈 훅(beacon) + 고정 TTL 안전망

## 상태

확정 — 구현 완료 (`feature/queue-leave-release`)

> 컨텍스트·고려안·트레이드오프·한계는 Claude 정리, **결정은 작성자 확정.**

## 컨텍스트

### 남은 유령 세션: 이탈 유저

PR #16(confirm 시 토큰 즉시 회수)으로 **구매 완료** 유저의 유령 세션은 제거됐다.
남은 문제는 **구매 없이 떠난 유저**다. 명시적 종료 신호가 없어 두 자리에서 유령이 된다:

| 상태 | 잔존 자료구조 | 잔존 기간 | 피해 |
|------|--------------|----------|------|
| 입장 후 이탈 | `entry:{e}:{u}` + `active:all` 멤버 | TTL 최대 5분 | ceiling 슬롯 점유 → 대기자 입장 지연 |
| **대기 중 이탈** | `queue:{eventId}` ZSET 멤버 | **무기한** (ZSET에 TTL 없음) | 순번이 되면 **유령에게 토큰 발급** → 그때부터 5분 슬롯 점유 |

대기 중 이탈은 이번 검토에서 발견된 추가 문제다 — 이탈자를 대기열에서 지우지 않으면
배치 입장이 부재자에게 토큰을 발급하고, 그 토큰이 다시 5분짜리 유령 세션이 된다.

### 전제가 되는 도메인 규칙 (작성자 결정)

**입장 토큰 TTL 5분은 고정 상한이다 — 연장 없음.** 입장한 자리에서 할 일은 좌석 hold와
결제뿐이고, 5분이면 충분하다. 그 이상 머무는 것은 자리 점유(캠핑)이므로 내보내는 것이 맞다.
"활동 중인데 5분 만료로 잘리는" 케이스는 버그가 아니라 **의도된 퇴장**이다.

이 규칙이 설계 공간을 크게 줄인다: 세션을 "존재하는 동안 연장"하는 방식(sliding TTL)은
전제와 충돌하므로 기각되고, 문제는 "**고정 5분 안에서 이탈을 얼마나 빨리 감지하느냐**"로 좁혀진다.

## 고려한 방식

| 방식 | 내용 | 평가 |
|------|------|------|
| sliding TTL + heartbeat | TTL 단축(30~90s) + 활동 시 연장, 총 상한 캡 | ❌ "세션=존재" 의미론이 **5분 고정 상한 규칙과 충돌**. 연장 없는 세계에선 heartbeat가 할 일이 없음 |
| 서버 측 폴링 중단 감지 | 마지막 status/좌석 폴링 시각 추적 → 임계 초과 시 회수 | ❌ 별도 추적 자료구조 + 판정 스케줄러 필요. TTL이 이미 "신호 없으면 소멸"을 공짜로 제공하는데 중복 구현 |
| **클라이언트 이탈 훅** ✅ | `pagehide` 시 keepalive 요청으로 leave API 호출 | 정상 이탈(닫기·새로고침·외부 이동)을 **0초에 회수**. 크래시·강제종료는 못 잡음 → TTL 안전망에 위임 |
| 현행 유지 | TTL 5분 방치 | ❌ 이탈 유저가 최대 5분 슬롯 점유 + 대기열 유령은 무기한 |

## 구현 결정 (초안)

### 1. `POST /api/queue/{eventId}/leave` — 두 상태를 한 번에 정리

```java
public void leave(Long eventId, Long userId) {
    queueRepository.dequeue(eventId, userId);           // 대기 중이었다면: 순번 제거
    queueRepository.releaseEntryToken(eventId, userId); // 입장했었다면: 토큰 + 활성 세션 회수
}
```

- 호출자의 상태(대기 중/입장 후/무상태)를 구분하지 않는다 — 삭제는 멱등이라 무조건 둘 다 정리.
- **이벤트 존재 검증 없음**: 정리 연산이라 미존재면 지울 것도 없고(no-op), 이탈 스파이크가
  DB를 때릴 이유가 없다(ADR-014와 같은 원칙).

### 2. 프론트: `pagehide` + `fetch(keepalive)`

- **`pagehide`는 문서 언로드에만 발생** — SPA 라우트 전환(대기실→좌석 페이지)에는 발생하지
  않으므로 내부 이동은 이탈로 치지 않는다. 별도 화이트리스트 로직 불필요.
- **백그라운드 탭(딴짓)은 세션 유지** — 언로드가 아니므로 훅이 안 뜬다. "페이지를 닫아야 이탈"
  (작성자 결정). 딴짓하다 5분을 넘기면 어차피 고정 TTL이 퇴장시킨다.
- **`sendBeacon`이 아니라 `fetch(keepalive: true)`**: sendBeacon은 Authorization 헤더를 실을 수
  없는데 이 프로젝트 인증은 JWT 헤더다. keepalive fetch는 헤더를 실으면서 페이지 종료 후에도
  요청을 완주시킨다.
- 부착 지점: `QueueWaitingPage`(대기 순번 정리), `EventDetailPage`(queueEnabled && BOOKER일 때
  토큰 회수). Checkout 페이지엔 부착하지 않는다 — confirm은 토큰을 요구하지 않으므로(게이트는
  hold에만) 결제 중 새로고침이 구매를 깨지 않고, 완료 시 PR #16이 회수한다.

### 3. 함께 발견·수정한 불변식 위반: 토큰 보유자의 재enqueue

이 검토 중 기존 버그를 발견했다. 프론트 hold 흐름이 "좌석 선택 → `enter` 호출 → admitted면
hold"라서, **이미 입장한(토큰 보유, ZPOPMIN으로 대기열에선 빠진) 유저가 hold할 때마다 `enter`가
그를 대기열에 다시 넣었다.** 결과: 대기열 유령 멤버 → 나중에 스케줄러가 토큰 재발급 →
**5분 고정 상한이 리셋**되고 그 초의 rate 1개가 낭비.

수정: `enter`에서 토큰 보유자는 enqueue를 생략하고 상태만 반환한다. 서버가
**"입장 토큰 보유 XOR 대기열 대기"** 불변식을 보장하므로, 프론트가 어떤 순서로 enter를
호출해도 안전하다. 이 불변식은 대기열 진입 시점을 이벤트 페이지로 옮기는 후속 재설계(백로그)에서
enter 호출이 더 빈번해질 때 더욱 중요해진다.

### 4. 새로고침 = 이탈 (의도된 동작)

`pagehide`는 새로고침에도 발생하므로 **새로고침 유저도 재대기**한다. 새로고침을 이탈과 구분할
신뢰할 수 있는 방법은 없고(복귀 여부는 미래의 일), 티켓팅 도메인에서 "새로고침하면 줄 다시
서기"는 통용되는 규칙이다(작성자 결정). 이미 hold한 좌석과 결제는 영향받지 않는다(§2).

## ⚠️ 한계

- **best-effort다.** 크래시·모바일 강제종료·네트워크 단절은 `pagehide`가 발생하지 않거나 요청이
  유실된다 → 이 경우 토큰 TTL(5분)이 안전망. 즉 유령 세션의 **상한이 5분에서 바뀐 게 아니라,
  정상 이탈(대부분의 경우)이 0초로 당겨진 것**이다.
- 이탈 훅의 실제 발화율(브라우저·플랫폼별 pagehide 신뢰도)은 측정하지 않았다.
- **대기실 새로고침 race**: leave(keepalive)와 리로드 후 재진입 enter의 서버 도착 순서는 보장되지
  않는다. leave가 늦게 도착하면 방금 선 줄을 지울 수 있어, 대기실 폴링에 자가 치유를 넣었다 —
  대기 중인데 position이 null이면 다시 enter한다(맨 뒤 재진입, 이탈 취급과 일관).
- 대기 중 이탈자의 유령 순번도 leave가 놓치면(크래시) 무기한 남는 문제가 이론상 잔존한다.
  현 규모에선 수용하고, 필요해지면 대기열 멤버에 진입 시각 기반 청소(오래된 멤버 ZREMRANGEBYSCORE)를
  스케줄러에 추가할 수 있다.

## 결정

**클라이언트 이탈 훅(pagehide + keepalive fetch → leave API)을 채택하고, 크래시 등 훅이 못 잡는
이탈은 기존 토큰 TTL(5분 고정)을 안전망으로 유지한다.**

- sliding TTL(heartbeat 연장)은 기각 — "입장 세션은 5분 고정 상한, 초과는 캠핑"이라는 도메인
  규칙과 충돌한다. 연장이 없는 이상 heartbeat는 불필요한 인프라다.
- leave는 대기 순번과 입장 토큰을 **무조건 함께** 정리한다(멱등). 대기 중 이탈자를 지우지 않으면
  유령에게 토큰이 발급되는 2차 유령 문제가 이번 검토에서 확인됐기 때문이다.
- 새로고침도 이탈로 취급한다(재대기). hold된 좌석과 confirm은 영향받지 않는다.
