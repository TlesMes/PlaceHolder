# 제공자 정산 적립의 처리량 상한 — 측정 계획 및 재설계안

> 상태: **측정 완료 (2026-08-22) — 제공자 행이 병목으로 판정. 재설계는 별도 계획**
> 작성: 2026-08-21 (제공자 정산액 lost update 수정 세션)
> 개정: 2026-08-22 — 측정 대상을 **knee point(절대값) → 제공자 수에 대한 형태(비율)** 로 전환하고
> 판정 기준을 측정 전에 고정 (2·6절)
> 관련: [ADR-020](../adr/ADR-020-point-bucket-separation.md), [ADR-008](../adr/ADR-008-lock-strategy.md),
> [정산 조회 무페이징 한계](./settlement-query-scalability.md), `loadtest/HANDOFF-D2.md`

## 한 줄 요지

제공자 정산액 lost update를 **비관적 락으로 막았다**(`b6f879d`). 정합성은 확보됐지만
**같은 제공자의 좌석 판매가 계정 행 하나에서 직렬화된다.** 이 상한이 실제로 문제가 되는지
측정하고, 문제라면 **정산 잔액을 원장에서 파생**시키는 방향으로 재설계한다.

**핵심은 순서다 — 지금 재설계하지 않는다.** 상한이 존재한다는 것과 그것이 병목이라는 것은
다른 주장이고, 후자는 아직 측정된 적이 없다.

## 1. 어쩌다 상한이 생겼나

### 고친 결함 (배경)

`settlementBalance += amount`가 락 없이 read-modify-write 되고 있었다. JPA 더티 체킹은
절대값(`SET settlement_balance = ?`)을 쓰므로, 서로 다른 예약자가 같은 제공자의 **다른** 좌석을
동시에 확정하면 적립이 서로 덮어써졌다. 좌석 락도(다른 행) 예약자 계정 락도(다른 행)
이들을 직렬화하지 못한다.

재현 결과(`ProviderSettlementConcurrencyTest`, 수정 전):

```
동시 확정 10건 → 전부 성공
SETTLE 이력    → 10행 (정상)
정산 잔액      → 5,000   ← 50,000이어야 한다. 9건 유실
```

**이력은 INSERT라 덮어쓸 것이 없고, 잔액은 UPDATE라 덮어써진다.** 같은 사실을 두 곳에
저장하면서 갱신 방식이 달라 갈라진 것이다.

### 수정과 그 대가

`findByUserIdForUpdate`를 추가하고 확정 경로가 이를 쓰도록 했다. 락 순서 규약은
**좌석 → 예약자 계정 → 제공자 계정**으로 확장됐다(제공자 계정을 잠그는 경로는 확정뿐이라
순환 대기 없음). 락 획득은 트랜잭션의 **가장 마지막**으로 옮겨 보유 구간을 최소화했다 —
락은 획득부터 커밋까지 유지되므로 "언제 잡느냐"가 곧 보유 시간이다.

**남은 것:** 인기 이벤트에서 한 제공자의 모든 확정이 그 한 행을 두고 줄 선다.
대기열(E-1)이 유입을 셰이핑해도 **확정 자체는 직렬화된다.**

## 2. 측정 계획

### 무엇을 재는가 — 지점이 아니라 형태

이 상한이 몇 건에서 꺾이는지는 **재지 않는다.** 부하생성기를 별도 머신으로 분리할 수 없는
환경에서 한 PC로 뽑은 절대 처리량은 그 PC에서만 참이고, **재설계 판단의 입력이 못 된다.**
D-2가 정확히 그 조건에서 "생성기가 먼저 병목이라 서버 한계를 재지 못했다"로 끝났다.

대신 형태를 잰다: **제공자 수를 늘리면 처리량에 무슨 일이 일어나는가.**
"제공자를 2배로 늘렸더니 처리량이 2배"는 두 실험군이 **같은 오염을 공유**하므로 비율에서
상쇄돼 한 PC에서도 살아남는다. 원래 이 문서가 "측정의 심장"이라 적어둔 대조 변수가 이것이고,
knee point는 그 옆에 붙어 있던 D-2의 잔재였다.

### 자릿수는 여전히 필요하다

형태만으로는 판단이 안 선다. 처리량이 제공자 수에 선형으로 오르더라도 제공자당 상한이
초당 2,000이면 재설계는 과잉이고, 20이면 즉시 착수다.

자릿수는 부하를 밀어서가 아니라 **직렬 구간의 보유 시간**에서 나온다:

```
제공자당 상한 ≈ 1 / 락 보유시간
```

보유 시간은 저부하에서도 측정되므로 **생성기 병목과 무관하다.**
D-2에 없었던 것이 바로 이 내부 귀속 지표다 — 그때는 외부 지연 곡선 하나뿐이라
꺾인 원인을 서버에 귀속시킬 수단이 없었다.

### 설계

| 항목 | 내용 |
|---|---|
| 환경 | **JUnit + Testcontainers 인프로세스** (`SettlementThroughputBenchmark`). HTTP·Tomcat·JSON 제거 |
| 부하 | `reservationService.confirmReservation()`을 고정 스레드풀(`T=32`)로 직접 호출 |
| 총 건수 | `N = 240` (1·2·4·8로 나누어떨어짐), 확정 1건당 예약자 1명 |
| **대조 변수** | **제공자 수 `P` ∈ {1, 2, 4, 8}** — 좌석 `N/P`석씩 분배 |
| 비교군 ① | 락 있음 (현재 프로덕션 경로) |
| 비교군 ② | **락 제거 상한** — spy로 `findByUserIdForUpdate`를 비잠금 `findByUserId`에 위임, `P=1`. 파생 재설계를 만들기 전에 "얻을 수 있는 최대치"를 확보 |
| 지표 | 처리량(**비율로만**), 확정 지연 p50/p95/p99, **락 대기 시간**, **락 보유 시간** |
| 반복 | 설정당 3회 중앙값 + 워밍업 1회 폐기 |

**부하생성기가 원리적으로 사라진다.** 스레드풀이 곧 부하이고, 큐잉은 JVM 안에서 일어나
coordinated omission이 성립하지 않는다. `ProviderSettlementConcurrencyTest`가 이미 이
축(서로 다른 예약자 × 같은 제공자 × 다른 좌석)을 재현하므로, **부하 규모만 키우면 그대로
측정 하네스다.**

**통제:** Hikari 기본 풀 10 < `T=32`이면 풀이 먼저 병목이 된다 → 하네스에서 48로 올리고
측정 조건에 명시한다(D-2에서 풀 크기로 결론이 세 번 뒤집힌 전례).

### 판정 기준 — 측정 전에 고정한다

숫자를 본 뒤 기준을 정하면 결론이 숫자를 따라간다. ADR-020의 음성 대조군 선행과 같은 기조로,
대입할 기준을 먼저 적는다. `R = 처리량(P=8) / 처리량(P=1)`:

| 관측 | 결론 |
|---|---|
| `R`이 P에 뚜렷이 비례(≥4) **AND** `P=1`에서 락 대기가 지연의 지배항 | **제공자 행이 병목** → 3절 재설계 후보 |
| `R ≈ 1` | 병목은 다른 곳(커밋 비용·풀·CPU). **재설계해도 안 나아진다** → 종료 |
| `R`은 오르는데 ②가 ①(`P=1`)과 큰 차이 없음 | 직렬화의 주범이 락이 아님 → 종료 |

**요구 기준선(이것도 먼저 적는다):** 한 제공자의 인기 이벤트가 좌석 1,000석을 오픈 직후
10초에 소진한다고 보면 필요 확정률은 **≈100건/초**(한 제공자 기준). 측정된 제공자당 상한이
이 값을 자릿수로 웃돌면 **"상한은 있으나 병목은 아니다"로 문서를 닫는다.**

### 반대편도 재야 서사가 완결된다

파생으로 바꾸면 비용이 **쓰기 경합 → 읽기 누적**으로 이동한다. 그러니 재설계 후에는
정산 조회 응답을 **SETTLE 행 수를 늘려가며** 측정해 "상한을 없앤 대가"를 수치로 남긴다.
이 축은 [정산 조회 무페이징 한계](./settlement-query-scalability.md)와 자연스럽게 합쳐진다.

## 3. 재설계안 — 정산 잔액을 원장에서 파생

확정 트랜잭션은 `SETTLE` 행을 **INSERT만** 한다. 제공자 계정을 건드리지 않으니
경합이 **소멸**한다(상한을 올리는 게 아니라 없앤다).

이는 ADR-020이 예약자 측에 적용한 원칙을 제공자 측에도 적용하는 것이다:

> 버킷이 진실이고 `getBalance()`는 파생이다. 둘 다 저장하면 어느 한쪽만 갱신하는 코드가
> 생겨 진실이 갈라진다.

현재 제공자 쪽이 바로 그 "둘 다 저장해서 갈라졌던" 상태였다(위 재현 결과).

**전제 사실:** `settlementBalance`는 [ProviderAccountService](../../src/main/java/com/placeholder/domain/provider/service/ProviderAccountService.java)의
대시보드 응답에서만 읽힌다. **아무 판단도 이 값에 걸리지 않는다** — 검증도 게이트도 차감도 없다.
그래서 파생으로 바꿔도 실시간 정합성 요구가 없다.

### 무한 성장 문제와 해법

`SETTLE` 원장은 append-only라 SUM 대상이 계속 늘어난다. 표준 해법은 **스냅샷 + 증분**이다.

```
정산 잔액 = 스냅샷 잔액 + SUM(스냅샷 이후 SETTLE)
```

- `settlement_snapshots(provider_id, as_of, balance)`를 배치가 주기적으로 기록
- SUM 대상이 **스냅샷 주기 이내로 유계**가 된다 (일 단위면 최대 하루치)
- 스냅샷 기록은 배치라 확정 경로와 **경합하지 않는다**
- 배치 골격은 `PaymentReconciliationScheduler` 패턴 재사용 (cron + `zone=Asia/Seoul` 명시)
- 커버링 인덱스 `(user_id, type, amount)` 동반

**도메인상 더 자연스러운 유계 조건:** 정산예정액은 원래 **미지급분**이다. 정산 지급(`PAYOUT`)이
생기면 지급된 `SETTLE`은 합산 대상에서 빠져 자연히 유계가 된다. 지금은 지급이 미구현이라
(CLAUDE.md: "정산: 집계까지만, 현금 출금 없음") 무한히 쌓인다.
→ 이는 **ADR-020 갚을 신호 1번("제공자 측 거래 종류가 늘 때")과 같은 지점**이다.

## 4. 저장소 평가 — DB vs Redis

집계 전 증분을 어디에 담을 것인가에 대한 평가. **결론: 원장은 DB. 선택지가 아니다.**

### Redis를 원장 자리에 두면 안 되는 이유

| | 근거 |
|---|---|
| **이미 DB 적재 중** | `SETTLE` 행은 확정 트랜잭션 **안에서** 저장된다 — 좌석 CONFIRMED·예약 생성·포인트 차감과 원자적. 새로 만들 것이 아니라 이미 가진 것이다 |
| **dual write** | 커밋은 MySQL, 증분은 Redis → 커밋 성공 후 `INCRBY` 전에 죽으면 **좌석은 팔렸는데 정산이 없다.** 재시도로 수렴하지 않는다(원본이 없으므로) |
| **AOF는 돈의 유일한 기록이 되기엔 약하다** | `--appendonly yes`지만 fsync 기본이 `everysec` → 최대 1초 치 유실. 대기열 토큰이면 TTL 안전망으로 흡수되지만(ADR-013) 정산액은 재계산할 방법이 없다 |
| **ADR-013 원칙 반전** | 이 프로젝트는 "대기열 = 트래픽 셰이핑, 정합성은 DB"로 층을 나눠뒀다. Redis를 원장으로 쓰면 **돈의 정합성을 Redis에 맡기는 것**이라 그 구분이 무너진다 |

### Redis의 정당한 자리 — 읽기 캐시

거꾸로면 성립한다. **DB 원장이 진실, Redis는 계산된 SUM을 캐싱.**

- 확정 시 `INCRBY`로 캐시 갱신하되, 틀려도 **DB에서 재계산해 복구 가능**
- 캐시 미스·Redis 장애 → DB에서 SUM 재구성 (ADR-014 read-through 기조)
- **재구성 가능한 파생값**이라 유실이 손실이 아니다

**단 지금은 시기상조다** — 정산 조회가 느리다는 측정이 없다. PR #14에서 enter fast-path를
"시기상조"로 제거한 것과 같은 판단.

### 결론

| 층 | 저장소 | 이유 |
|---|---|---|
| 원장 (`SETTLE` 행) | **DB** | 확정 트랜잭션과 원자적. 유일한 진실 |
| 스냅샷 (주기 집계) | **DB** | 배치가 쓰므로 확정 경로와 무경합. 재계산 가능 |
| 읽기 캐시 | (측정 후) Redis | 재구성 가능한 파생값일 때만 |

## 5. 단계

1. ~~lost update 차단 (비관적 락)~~ — 완료 `b6f879d`
2. **측정** — 2절 설계대로. 제공자 수 대조 변수 필수. 인프로세스 하네스라 **별도 부하 환경 불필요**
3. **판단** — 상한이 실제 병목이면 4단계, 아니면 여기서 종료하고 측정 결과만 문서화

   3절은 스케치이므로 **측정 결과를 보고 다시 계획한다**
5. **역방향 측정** — 정산 조회 응답 곡선(행 수 증가). settlement-query-scalability와 병합

## 6. 미결

- **스냅샷 주기:** 일 단위가 기본 후보. 실제 판매량을 보고 정한다.
- **`PAYOUT` 도입 시점:** 지급이 생기면 유계 조건이 도메인에서 자연히 나온다. 그때 4단계를
  함께 하는 것이 ADR-020이 말한 "갚을 시점"과 맞는다.

### 해소된 미결 — 측정 환경

"앱·DB·부하생성기가 한 PC를 공유하면 해석이 흐려진다"는 우려는 인프로세스 하네스로 **대부분
해소된다.** 부하생성기가 원리적으로 사라지고(스레드풀이 곧 부하), HTTP·Tomcat·JSON이 경로에서
빠진다. 남는 공유는 JVM ↔ MySQL 컨테이너뿐이며 **두 실험군에 동일하게 걸리므로 비율 해석에는
영향이 없다.**

### 대신 생긴 한계 (해석 시 반드시 함께 읽을 것)

- **재는 것은 확정 트랜잭션의 처리량이지 API 처리량이 아니다.** 이 숫자를 "초당 몇 명이 예약
  가능"으로 읽으면 안 된다. 인증·직렬화·네트워크가 빠져 있고, 그건 **의도된 제거**다 —
  묻는 대상이 DB 행 하나이기 때문이다.
- **커밋 fsync가 보유 시간의 상당 부분일 수 있다**(`innodb_flush_log_at_trx_commit=1` 기본값).
  그렇다면 상한의 원인은 락이 아니라 **커밋 비용**이고, 파생 재설계로도 안 없어진다.
  대조 변수(`P`)와 비잠금 비교군(②)이 이 둘을 갈라준다 — 판정 기준표의 아래 두 행이 그 경우다.
- **단일 인스턴스 JVM 전제.** 다중 인스턴스에서는 같은 행을 두고 프로세스 간 경합이 붙어
  대기가 더 길어진다(E-4 분산 환경 축).

> 조건: 총 확정 240건, 스레드 32, **Hikari 풀 48**, 설정당 3회 중앙값, 워밍업 1회 폐기,

### 판정

2절 기준표 첫 행(**`R`이 P에 뚜렷이 비례 AND `P=1`에서 락 대기가 지배항**)에 걸린다 →
**제공자 계정 행이 확정 처리량의 병목이다.**

- **락 대기가 지연을 지배한다:** `P=1`에서 확정 지연의 **93%**가 잠금 조회에서 막힌 시간이다
  (303.7/325.5, 343.0/368.9). P가 커질수록 이 값만 단조 감소한다(303→27ms) — 줄어드는 것이
  대기지 작업이 아니라는 뜻이다.
- **해석적 상한과 실측이 만난다:** `1/락보유시간`으로 계산한 제공자당 상한은 **91 / 83건/초**인데
  실측 `P=1` 처리량이 **88.1 / 81.2건/초**다. 두 회차 모두 오차 4% 안에서 일치한다.
  **부하를 밀어 찾은 값이 아니라 보유 시간에서 유도한 값이 실측과 만났다는 것**이 이 측정의
  핵심 증거다 — D-2에 없었던 내부 귀속이 여기서 닫힌다.
- **요구 기준선 미달:** 측정 전에 못 박은 기준선은 ≈100건/초였고 제공자당 상한은 **≈85건/초**다.
  자릿수로 웃돌지 못하므로 "상한은 있으나 병목은 아니다"로 닫을 수 없다.

### 정직하게 남기는 것

- **`R`은 회차 간에 흔들린다(3.13–3.99).** 기준표에 적은 `≥4`를 엄밀히 충족한 것은 1회차뿐이다.
  다만 판정의 실질은 "P에 비례해 오르는가"이고 두 회차 모두 3배 이상 올랐으며, 결론을 떠받치는
  것은 배수 자체가 아니라 위의 상한·실측 일치다.
- **`P=8`이 선형(8x)에 못 미치는 것은 예상된 결과다.** 행 경합이 풀리자 이번엔 이 PC가 한계에
  들어온다 — 락 보유 시간 자체가 12→30ms로 늘고(동시 커밋 증가) 대기는 계속 줄어든다.
  뒤집어 말하면 **행 상한(≈85건/초)은 박스 용량(≈250–350건/초)의 1/3–1/4 지점**에 있다.
- **⚠️ 비교군 ②는 재설계 상한이 아니었다 — 설계 단계에서 못 본 지점이다.** 잠금 조회를
  없앴을 뿐 `UPDATE settlement_balance`가 남아 **플러시 시점에 같은 행을 다시 X락으로
  직렬화**한다(락 대기가 0.8ms로 사라지고 "보유"로 잡힌 구간이 283ms로 부푼 것이 그 증거다).
  그래서 1.2–1.4x는 파생 재설계 이득의 **하한**이지 상한이 아니다. 진짜 상한은 그 행에 대한
  쓰기가 통째로 사라지는 쪽(3절)이고, 이 하네스로는 재설계를 실제로 만들기 전에는 못 잰다.
- 재는 것은 **확정 트랜잭션의 처리량이지 API 처리량이 아니다**(6절). "초당 85명 예약 가능"으로
  읽으면 안 된다.

### 다음

병목으로 판정됐으므로 5절 4단계(파생 재설계)가 열린다. **다만 3절은 스케치이므로 별도로 다시
계획한다** — 특히 위에서 드러난 대로 "없애야 하는 것은 잠금 조회가 아니라 그 행에 대한 쓰기"라는
점이 재설계의 성패를 가른다.
