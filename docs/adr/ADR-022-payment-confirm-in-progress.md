# ADR-022. 승인 요청 중 상태(IN_PROGRESS) 도입 — 결과 모름을 실패로 처리하지 않는다

## 상태

**제안** — 구현 완료, 결론부 작성자 검토 대기

> 트랜잭션 경계와 상태 설계에 해당하는 결정이라 결론은 작성자가 확정한다. 재현·구현·문서 초안은 Claude.

## 컨텍스트

### 발견 경위

결제사 호출의 읽기 타임아웃 값(5초)의 근거를 확인하다가 발견했다. 값 자체의 근거는 문서에 없었고
(토스는 결제 API 읽기 타임아웃 60초를 권장), 그보다 **타임아웃이 났을 때의 처리**가 문제였다.

ADR-018의 승인 흐름은 `[tx] 검증 → 트랜잭션 밖 토스 호출 → [tx] 적립`이다. 앞 트랜잭션은 읽기 전용이라
아무것도 기록하지 않았다. 그 결과 DB에는 **"토스에 승인을 요청했다"를 표현할 상태가 없었고**,
READY 하나가 세 가지를 뜻했다.

1. 사용자가 아직 결제창에 있다
2. 우리 서버가 지금 토스에 승인을 요청하는 중이다
3. 승인을 요청했는데 응답을 못 받아 결과를 모른다

### 재현 (`PaymentConfirmUnknownResultTest`, 수정 전 3건 모두 실패)

실제 `TossPaymentClientImpl`에 스텁 HTTP 서버로 실제 읽기 타임아웃을 일으켰다. 스텁은 승인을 즉시
처리하고 응답만 늦게 보낸다(토스는 승인했는데 응답이 유실된 상황).

| 시나리오 | 수정 전 결과 |
|---|---|
| 타임아웃 → 웹훅 도착 | 타임아웃이 승인 실패로 번역돼 주문 FAILED. 웹훅의 `markDone`은 "READY 아님"으로 거부 |
| 타임아웃 → 대사 | 주문 FAILED. 대사는 READY만 조사하므로 보지도 않음 |
| 첫 승인 진행 중 새로고침 | 두 번째 요청도 READY를 보고 토스를 호출(**2회**). 그 거절이 주문을 FAILED로 만들고, 뒤늦게 DONE을 받은 첫 요청의 적립이 거부됨 |

세 경우 모두 **고객 돈은 빠져나갔는데 포인트는 0이고, 자동으로 발견·복구하는 경로가 없다.**

## 결정

### 1. `IN_PROGRESS` 상태 — "토스에 승인을 요청했고 결과는 아직 모른다"

```
READY ─(앞 tx 커밋)→ IN_PROGRESS ─┬─ 토스 DONE ────→ DONE
                                   ├─ 토스가 거절 ──→ FAILED
                                   └─ 결과 모름 ───→ IN_PROGRESS 유지 → 웹훅·대사가 확정
```

### 2. 앞 트랜잭션이 쓰기를 맡는다 (`beginConfirm`)

주문 행을 잠그고 본인·금액·상태를 판정한 뒤 READY면 IN_PROGRESS로 전이해 **토스 호출 전에 커밋**한다.

- **확인과 전이가 한 트랜잭션** — 동시에 온 요청 중 하나만 전이에 성공해 토스를 호출한다.
  나머지는 IN_PROGRESS를 보고 토스를 부르지 않는다.
- **커밋 시점 = "요청이 나갔다"를 공개하는 시점.** 그래서 토스 호출 전에 끝나야 하고,
  커밋과 함께 락이 풀려 토스를 기다리는 동안 락·커넥션을 쥐지 않는다(ADR-018 3번 유지).

이전의 읽기 전용 트랜잭션은 지킬 쓰기가 없어 트랜잭션으로서 의미가 없었다. 이 전이로 처음 의미가 생긴다.
ADR-019 취소 흐름(상태 전이를 외부 호출보다 먼저 커밋)과 같은 원칙을 승인에 적용한 것이다.

### 3. 결제사 실패를 두 종류로 나눈다 (`TossPaymentClientImpl.confirm`)

| 응답 | 의미 | 예외 | 주문 |
|---|---|---|---|
| 4xx | 토스가 명시적으로 거절 | `PaymentConfirmFailedException` | FAILED |
| 4xx `ALREADY_PROCESSED_PAYMENT` | 이미 승인됐다는 뜻일 수 있음 | `PaymentResultUnknownException` | IN_PROGRESS 유지 |
| 5xx·타임아웃·전송 중 끊김·빈 본문 | 처리 여부 모름 | `PaymentResultUnknownException` | IN_PROGRESS 유지 |

**확실한 거절만 열거하고 나머지는 전부 결과 모름**으로 보낸다. 열거에서 빠진 예외가 생겨도 안전한
쪽(대사가 확인)으로 떨어지게 하기 위해서다. 손실이 비대칭이다 — 결과 모름을 실패로 분류하면 금전 손실,
거절을 결과 모름으로 분류하면 사용자가 잠시 "확인 중"을 볼 뿐이다.

### 4. 기존 가드 조정

- `markDone`·`markFailed`·`markExpired`: READY만 받던 것을 결과 미확정(READY·IN_PROGRESS)으로 확장
- 정방향 대사 후보: READY → READY·IN_PROGRESS
- 만료 권한 분리(ADR-018 개정)는 IN_PROGRESS에도 같다 — 보정 잡은 404여도 종결하지 않는다
- 이미 FAILED·EXPIRED인 주문의 재승인 요청은 토스를 부르지 않고 거부한다(이전엔 토스를 다시 불렀다)

## 기각한 대안

| 대안 | 기각 이유 |
|---|---|
| 읽기 타임아웃만 60초로 상향(토스 권장) | 결함의 빈도만 낮춘다. 60초 초과·전송 중 끊김·5xx는 그대로 FAILED. 게다가 토스 장애 시 요청 스레드가 견디는 승인 요청이 약 40 → 3.3건/초로 줄어(Tomcat 200 기준 계산값) 장애 전파 범위가 넓어진다 |
| 결과 모름이면 READY로 남기기만 함 | 타임아웃 결함은 닫히지만 "요청 중"을 여전히 표현하지 못해 새로고침 경합(토스 2회 호출)이 남는다 |
| 토스 호출을 트랜잭션 안에 넣기 | 결제사 응답을 기다리는 동안 커넥션을 점유한다. 같은 PC 측정(풀 10, 결제 20건 동시)에서 지연 2000ms일 때 좌석 홀드 처리량 525.5 → 38.5건/초, p95 100 → 2075ms (`PaymentTxBoundaryBenchmark`) |
| 조건부 UPDATE 한 문장(`WHERE status='READY'`) | 원자성은 문장이 보장하지만, 0행일 때 이유(타인 주문·금액 불일치·처리 중)를 구분할 수 없어 사용자에게 다른 응답을 줄 수 없다 |

## 결과

- 재현 테스트 3건이 통과로 바뀌었다. 승인 응답이 유실돼도 웹훅 또는 대사가 적립을 확정한다.
- **사용자 체감 변화:** 결과를 모르는 결제는 "결제 확인 중"으로 보인다. 웹훅이 오면 즉시, 웹훅마저
  유실되면 대사 보정 잡(5분 주기, 생성 5분 후부터)이 확정한다. 토스에 요청이 닿지 않은 경우 토스가
  결제를 만료시킨 뒤에야 FAILED가 되므로 실패 확정까지 수십 분이 걸릴 수 있다.
- **타임아웃 값이 정합성과 분리됐다.** 이제 읽기 타임아웃은 "얼마나 오래 기다릴까"를 정하는
  UX·자원 문제다. 현재 5초 유지 여부는 이 ADR에서 결정하지 않는다.
- **기존 DB에는 `ALTER`가 필요하다.** Hibernate가 `payment_orders.status`를 MySQL 네이티브
  `enum(...)`으로 만든다(테스트 DDL 로그로 확인). 이 프로젝트는 `ddl-auto: create`라 기동 시 다시
  만들어지지만, 스키마를 유지하는 환경이라면 `IN_PROGRESS`를 enum 값에 추가해야 한다.

## 확인하지 못한 것

- 진행 중인 승인에 같은 `paymentKey`로 다시 승인을 요청했을 때 토스의 실제 응답. 재현 테스트의 스텁은
  `ALREADY_PROCESSED_PAYMENT`로 가정했다. 수정 후에는 두 번째 요청이 토스까지 가지 않으므로
  결론에는 영향이 없다.
- 실 토스 환경에서의 타임아웃 E2E(스텁 서버로만 검증).
