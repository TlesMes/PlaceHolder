# ADR 인덱스

> Architecture Decision Records — **왜 그렇게 결정했는가**를 남긴다.
> 채택안뿐 아니라 **기각한 대안과 그 이유**를 함께 적는 것이 이 문서들의 목적이다.

전체 20종. 아래는 주제별 묶음이며, 번호 순서가 곧 결정이 쌓인 순서다.

---

## 동시성 — 이 프로젝트의 핵심 축

| ADR | 결정 | 기각한 대안 |
|---|---|---|
| [008](ADR-008-lock-strategy.md) | 좌석 홀드는 **비관적 락**(`SELECT ... FOR UPDATE`), 락 단위는 좌석 행 | 낙관적 락(재시도 폭증), DB 유니크 제약(상태 전이 표현 불가) |
| [009](ADR-009-expiry-strategy.md) | 만료는 **스케줄러 폴링 + lazy 검증 병행** | 스케줄러 단독(지연 시 구멍), DB TTL(상태 전이 훅 없음) |
| [010](ADR-010-coupon-concurrency.md) | 쿠폰 상환도 **비관적 락**으로 통일 | 원자적 UPDATE(한 트랜잭션에 카운터·유니크·잔액이 엇갈려 데드락 빈발) |

> 락 순서 규약: **좌석 → 예약자 계정 → 제공자 계정.** 전 경로가 같은 순서를 지켜 순환 대기를 막는다.

## 서로 이어지는 결정들

몇몇 ADR은 독립적이지 않다. 하나가 다른 하나를 낳거나 뒤집는다.

```
004 (대기열 제외)  ──재검토──▶  013 (대기열 도입)  ──개정──▶  게이트를 이벤트 진입점으로
                                     │
                                     ├──▶ 014 (존재 검증 캐싱)
                                     ├──▶ 015 (이탈 감지) ──▶ 016 (좌석 반환 분리)
                                     └──▶ 017 (기아 방지 분배)

008 (좌석 비관적 락) ──기조 계승──▶ 010 (쿠폰), 018·019 (주문 락), 020 (계정 락)

018 (결제 정합성) ──생애주기 확장──▶ 019 (취소·환불)
                                        │
                                        └─self-review─▶ 020 (재원 분리)
```

**020은 019의 self-review에서 나왔다.** 환불액 상한을 검토하다 잔액이 재원을 구분하지 않는다는
사실을 발견했고, 그것이 곧 금전적 구멍이었다. 그리고 020의 결론부를 검토하다 다시
**제공자 정산액 lost update**(PR #28)를 찾았다 — 결정을 문서로 남기는 작업이 결함을 드러낸 사례다.

## 작성 규칙

- **결정 지점마다** 작성한다. 코드를 쓰기 전에 쓰는 것이 원칙이나, 구현 중 드러난 사실은 되돌려 반영한다
- **기각한 대안과 이유**를 반드시 남긴다. 채택안만 적으면 "왜 이게 최선인지"가 사라진다
- **한계를 숨기지 않는다.** 측정하지 않은 것은 미측정이라고, 미룬 것은 미룬 이유와 함께 적는다
- 결론(정책 판단)은 작성자가 쓴다. 구조 정리와 대안 비교는 보조를 받는다
