# ADR-018. 결제 PG 연동 — 동기 승인 + 웹훅 이중화, 멱등 수렴

## 상태

확정 — 구현 완료 (PR: `feature/payment-toss-integration`)

> 컨텍스트·비교는 Claude 정리, **결정은 작성자 확정.** 실 샌드박스 키 미확보 상태에서
> 외부 호출은 인터페이스 목킹으로 검증(실호출 교체는 키 확보 후).

## 컨텍스트

기존 포인트 충전 경로는 캠페인 쿠폰 상환(`CouponRedeemService`)뿐이라 "현금 → 포인트" 실결제
플로우가 없었다. 마스터플랜 E-2의 핵심 어필은 **결제-포인트 정합성/멱등성**이다.

### 결제 플로우는 OAuth 인가코드 플로우와 동형

토스 결제는 구조상 OAuth와 같다: 프론트가 공개 `clientKey`로 결제창을 열어(=client_id redirect)
사용자 인증을 받고 `paymentKey`(=authorization code)를 받아오면, **서버가 시크릿 키로 confirm을
호출해 확정**(=code+client_secret → token 교환)한다. 다른 점은 오직 **부작용이 "비가역적 돈"**
이라는 것이며, 그로부터 아래 정합성 요구가 파생된다.

### 파생되는 정합성 요구 (돈이기 때문에)

- **멱등**: confirm의 부작용은 실제 결제다. 재시도·중복 콜백으로 두 번 적립되면 안 된다.
- **금액 위변조 방지**: 클라이언트가 보낸 금액을 신뢰할 수 없다(만원짜리를 10원 조작 시도 가능).
- **비동기 상태**: 결제는 서버 밖에서 시간차로 상태가 변한다(취소·지연) → 토스가 push로 통지(웹훅).
  OAuth엔 없는 순수 PG 요소.

## 결정

### 1. 동기 승인(주) + 웹훅(보조) 이중화, 멱등 수렴

confirm(동기, 즉시 반영)을 주 경로로 하고, 웹훅(보조)이 confirm 누락(사용자가 successUrl 도달 전
이탈 등)을 보정한다. **두 경로는 같은 멱등 적립 코어(`PaymentSettlementService.settle`)로 수렴**한다.
동기만 쓰면 누락 보정이 없고, 웹훅만 쓰면 즉시 반영이 안 된다 → 실무 정석인 이중화 채택.

### 1-2. 대사(reconciliation) — 삼중화의 마지막 층 *(2026-08-04 추가)*

동기·웹훅 이중화에는 구멍이 남는다. 토스는 승인을 마쳤는데 confirm 응답 전 서버가 죽고 웹훅마저
유실되면 주문은 READY로 남고 **시스템은 그 사실을 영원히 모른다.** 주기 배치로 토스에 되물어
스스로 발견·보정하는 세 번째 층을 둔다.

- **조회 축은 orderId다.** 누락 주문은 `paymentKey`가 null이라 기존 `getPayment(paymentKey)`로는
  접근조차 못 한다. 우리가 발급해 항상 보유한 orderId로 묻는다(`findByOrderId`). 토스에 기록이
  없으면(404) 예외가 아니라 `Optional.empty()` — "아직 결제창을 안 띄웠다"는 정상 상태 구분이다.
- **두 잡으로 분리하고, 만료 권한은 새벽 잡에만 준다.**
  | | 보정 잡 | 만료 잡 |
  |---|---|---|
  | 주기 | 5분(`fixedDelay`) | 새벽 4시(`cron`, `zone=Asia/Seoul`) |
  | 대상 | 생성 5분~2시간 | 생성 24시간 경과 |
  | 만료 권한 | **없음** | **있음** |

  **이 분리가 안전의 핵심이다.** 토스는 결제창이 열리기 전(주문 생성 직후 수 초)엔 그 orderId를
  몰라 404를 준다. 이때 성급히 종결시키면 곧이어 결제를 마친 사용자의 confirm이 `markDone()`에서
  거부되어 — **막으려던 사고(돈은 나갔는데 포인트 없음)를 대사가 일으킨다.** 자주 도는 보정 잡에서
  종결 권한을 아예 빼앗아 이 위험을 구조적으로 차단한다. 반면 "결제창에 머무는 사용자"는 토스에
  `IN_PROGRESS`로 잡혀 이미 스킵되므로, 유예시간의 역할은 진행 중 주문 보호가 아니라
  **404를 만료로 확정하기 전 안전 마진**이다.
- **보정 잡의 상한(2h)**: 충전 버튼만 누르고 이탈한 주문은 만료 전까지 READY로 남아 매 주기
  조회된다(5분 주기면 24h 동안 ≈288회). 상한을 넘기면 새벽 배치 소관으로 넘겨 조회를 ~24회로 묶는다.
- **새벽 잡도 나이만 보고 만료시키지 않는다.** 24h 된 READY가 실은 토스에서 DONE일 수 있어
  (보정 잡이 그 시간대에 죽어 있었다면) 반드시 재조회 후 판단한다 — 마지막 안전망.
- **금액 위변조 방어는 여기서도 적용.** 토스가 DONE이라 해도 금액이 주문 저장액과 다르면 적립하지
  않고 경고만 남긴다(confirm과 동일 원칙).
- **고아 주문은 `FAILED`가 아닌 `EXPIRED`로 구분한다.** "토스가 거절"과 "애초에 시도조차 없었다"를
  섞으면 원인 분석이 흐려진다. 좌석 hold 만료(ADR-009)와 같은 성격의 청소다.
- 적립은 기존 멱등 코어 `settle()`을 **그대로 호출**한다 — 이미 처리됐으면 no-op이라 중복 보정이
  원천 불가하다. 멱등을 코어로 분리해둔 설계(아래 2번)의 배당금이다.

### 2. 멱등 = orderId 비관적 락 + 상태 체크 (ADR-010 기조 재사용)

`PaymentOrder`를 `findByOrderIdForUpdate`로 잠그고 **"이미 DONE이면 no-op"**. confirm과 웹훅이 같은
orderId로 동시 도착해도 락이 직렬화하므로 정확히 1회 적립된다. 낙관적 락/유니크 제약과 비교했으나,
쿠폰 상환(ADR-010)에서 확립한 비관적 락 기조를 그대로 재사용하는 것이 일관적이고, 주문 단건 락이라
경합·데드락 위험이 낮다.

### 3. 트랜잭션 경계 — 외부 I/O는 트랜잭션 밖

**토스 confirm/조회 호출을 어떤 `@Transactional`에도 넣지 않는다.** 외부 호출을 트랜잭션 안에 두면
네트워크 지연만큼 DB 커넥션을 점유하고 락 보유 중 데드락 위험이 생긴다. 대신 순서를 나눈다:
① 사전 검증(락 없이 fail-fast) → ② **트랜잭션 밖** 토스 호출 → ③ 멱등 적립(짧은 단일 트랜잭션).
`@Transactional` self-invocation은 프록시 미경유로 무효이므로, 트랜잭션 메서드들은 별도 빈
(`PaymentSettlementService`)에 모으고 상위 서비스(`PaymentConfirmService`/`PaymentWebhookService`)는
트랜잭션 없이 이를 호출한다.

### 4. 웹훅은 permitAll + 페이로드 불신·재조회 검증

토스가 JWT 없이 호출하므로 웹훅 경로는 SecurityConfig permitAll. 대신 **페이로드를 신뢰하지 않고**
paymentKey만 꺼내 토스에 `getPayment`로 실제 상태를 재조회하고, 진짜 DONE일 때만 적립한다
(위조 웹훅 방어). 상용에선 서명 검증/IP 화이트리스트를 추가하나, 재조회 검증만으로 위조 페이로드에
의한 무단 적립은 막힌다.

### 5. 느린 외부 의존성 격리 — 타임아웃은 필수 구성

결제는 이 시스템에 처음 들어온 **느린 외부 의존성**이다. 지금까지 요청은 로컬 DB·Redis에서
끝났지만 토스 호출은 상대방 사정으로 느려질 수 있다. 트랜잭션 밖으로 뺀 덕에 DB 커넥션은 잡지
않으나(위 3번), **요청 스레드는 응답을 기다리는 동안 계속 붙잡힌다.** 타임아웃이 없으면 토스가
매달리는 만큼 스레드가 쌓여 좌석 hold 같은 무관한 경로까지 함께 굶는다.

이 장애 유형은 **대기열(E-1)이 막아주지 못한다** — 대기열은 유입 트래픽 셰이핑이고, 이건 하류
의존성 지연의 전파다. 그래서 `RestClient`에 connect 3초 / read 5초 상한을 건다(설정으로 조정
가능). 재시도·서킷브레이커·전용 스레드풀 격리는 이 단계에선 과하다고 보고 넣지 않았다 —
다만 타임아웃은 옵션이 아니라 기본값에 가까우므로 여기서 마감한다.

### 6. 외부 호출은 인터페이스로 추상화

`TossPaymentClient` 인터페이스 뒤로 실제 REST 호출(`TossPaymentClientImpl`, 내장 `RestClient`)을
숨긴다. 서비스는 인터페이스에만 의존(DIP)하므로 ① 테스트에서 목킹으로 멱등·경합·위변조 로직을 실제
네트워크 없이 검증하고, ② 실 샌드박스 키 확보 시 구현만 바꿔 끼운다.

### 포인트 매핑

현금 amount원 = amount포인트 (1:1). 환율/수수료 없는 단순화 가정.

## 불변식 (구현 시 유지)

- **분배=best-effort, 캡=보장의 책임 분리와 무관** — 결제 정합성은 전적으로 DB 비관적 락이 보장한다.
  토스 호출 실패는 confirm을 FAILED로 돌리고 적립하지 않는다(부분 적립 불가).
- **커밋 성공에만 적립** — settle은 단일 트랜잭션. 토스 확정(돈 빠짐) 후 적립 트랜잭션이 실패하면
  재요청/웹훅이 같은 orderId로 멱등 재적립한다(적립은 한 번, 재시도는 안전).
- **종결 상태 재전이 거부** — `PaymentOrder`는 READY에서만 DONE/FAILED로 전이(도메인 메서드가 강제).

## 한계

**이 ADR이 다룬 범위는 "정합성 축"까지다.** 멱등·금액 위변조·트랜잭션 경계·타임아웃은 정석대로
채웠으나, 결제의 **생애주기 축은 통째로 비어 있다** — 아래는 결정이 아니라 미구현이며, 실서비스
수준을 말하려면 함께 밝혀야 하는 공백이다.

- **취소·환불 경로가 없다(가장 큰 구멍).** 토스 취소 API 호출도, 포인트 회수도 구현하지 않았다.
  실서비스면 청약철회가 법적 요구이며, "이미 써버린 포인트"의 회수 정책·부분 취소 설계가 따라온다.
- ~~대사(reconciliation)가 없다.~~ → **해소(2026-08-04, 위 1-2번).** 다만 **역방향 대사**(우리는
  DONE인데 토스는 아님)는 v1 범위 밖이다 — 우리는 토스가 DONE이라 확인해준 뒤에만 DONE으로
  전이하므로 역방향 불일치는 사후 취소가 있어야 발생하는데, 취소 기능이 아직 없어 현재는 사실상
  도달 불가한 경로다. 취소·환불 구현 시 함께 붙인다.
- **비동기 결제수단(가상계좌 등) 미지원.** 상태머신이 `READY→DONE/FAILED`뿐이라 "입금 대기"라는
  중간 상태를 표현하지 못한다. 웹훅이 본래 가장 필요해지는 사례가 이것인데, 현재 웹훅은 동기 승인
  누락 보정 용도로만 쓰인다.
- ~~고아 주문 정리 없음.~~ → **해소(2026-08-04).** 대사 새벽 배치가 토스에도 기록이 없는 24시간 경과
  READY 주문을 `EXPIRED`로 종결한다.
- 웹훅 진위는 재조회 검증까지. 서명 검증·IP 화이트리스트는 후속.
- 충전 한도·감사 로그·영수증 없음. 포인트 충전은 규제상 단순 결제와 다르게 취급될 수 있어
  (선불 성격의 자금 보관 → 이용자 자금 보호 의무 등) 실제 요건 확인이 필요하다.
- 실 토스 샌드박스 호출은 이번 범위 밖(키 미발급) → `TossPaymentClientImpl`은 작성했으나 실호출
  E2E는 미검증. 키 확보 후 목 대체.
- 단일 인스턴스 전제. 멱등은 DB 락이라 다중 인스턴스에서도 안전하나, 실측은 미수행.
