# ADR-019. 결제 취소·환불 — 보상 트랜잭션과 되돌릴 수 없는 쪽을 나중에 치기

## 상태

확정 — 구현 완료 (PR: `feature/payment-cancel-refund`)

> 정책(환불 범위·주체·기한·보상 순서)은 **작성자 확정**, 구조·비교 정리는 Claude.
> ADR-018 "한계"에서 가장 큰 구멍으로 지목했던 항목을 메운다.

## 컨텍스트

ADR-018로 결제의 **정합성 축**(멱등·금액 위변조·트랜잭션 경계·타임아웃)과 삼중화(동기 승인·웹훅·대사)는
채웠지만, **생애주기 축**은 비어 있었다. 그중 취소·환불은 단순한 기능 누락이 아니다 —
전자상거래법상 청약철회는 법적 요구이고, 실서비스라면 없을 수 없는 경로다.

### 취소는 결제보다 어렵다 — 비대칭 때문에

결제와 취소는 같은 외부 호출처럼 보이지만 실패했을 때의 성질이 반대다.

| | 결제(적립) | 취소(환불) |
|---|---|---|
| 외부 성공 + 내부 실패 | 재시도/웹훅/대사가 **같은 orderId로 멱등 적립** → 수렴 | "돈은 돌려줬는데 포인트 회수 실패" → **순손실** |
| 복구 수단 | 멱등 재시도 | 없음 (토스 취소는 되돌릴 수 없다) |

결제는 "한 번 더 시도해도 안전"이 성립해서 실패가 지연으로 끝나지만, 취소는 한쪽만 성공한 순간
장부가 영구히 어긋난다. 그래서 이 결정의 전부는 **어느 쪽을 먼저 치느냐**로 수렴한다.

## 결정

### 1. 확정 정책 (작성자 결정)

| 항목 | 결정 | 근거 |
|---|---|---|
| 환불 범위 | **미사용분만 부분 환불** | 이미 좌석에 쓴 포인트는 회수 불가. 잔액만큼만 취소(토스 부분 취소 지원) |
| 취소 주체 | **API만, 본인 주문 한정** | 환불은 고객 문의를 경유하는 것이 맞다는 판단 → 셀프 UI 불필요 |
| 취소 기한 | **승인 후 7일** | 전자상거래법 청약철회 기간 |
| 보상 순서 | **포인트 선회수 → 토스 취소 → 실패 시 포인트 복구** | 아래 2번 |

### 2. 되돌릴 수 있는 쪽을 먼저 — 보상 순서의 근거

우리 DB는 롤백할 수 있고, **토스 취소는 되돌릴 수 없다.** 이 비대칭이 순서를 정한다.

```
① [트랜잭션] 검증 → 포인트 회수 → REFUND 기록 → 주문 취소 기록
②            토스 취소 호출                      ← 트랜잭션 밖 (ADR-018 3번 유지)
③ [트랜잭션] 성공: 취소 확정 기록 / 실패: ①을 통째로 되돌림
```

반대 순서(토스 먼저)를 택하면 ②가 성공하고 ③이 실패했을 때 **되돌릴 방법이 없다** — 돈은 이미
나갔는데 포인트는 그대로다. 지금 순서에서는 최악이 "포인트를 잠깐 회수했다가 되돌림"이고, 이건
전부 우리 DB 안의 일이라 복구가 결정론적이다.

외부 호출을 트랜잭션 밖에 두는 것은 ADR-018 3번 그대로다. 트랜잭션 메서드는 전부 별도 빈
(`PaymentSettlementService`)에 모으고 오케스트레이션(`PaymentCancelService`)은 트랜잭션을 갖지
않는다 — `@Transactional` self-invocation은 프록시를 안 거쳐 무효이기 때문.

### 3. 상태 전이를 ①에서 함께 한다 — 그것이 동시 취소의 방어선

취소 기록(`markCanceled`)을 토스 성공 이후로 미루면, ①~③ 사이에 들어온 두 번째 취소 요청이
**잔여액을 다시 계산해 토스에 중복 취소를 날린다.** 돈을 두 번 돌려주면서 포인트는 한 번만
회수하는 순손실이다. 주문 행 비관적 락 + "먼저 락을 얻은 쪽이 상태를 바꾸고 커밋" 순서가
이를 원천 차단한다. 실패 시엔 `revertCancel`이 상태와 잔액을 함께 되돌린다.

### 4. `canceledAt`과 `cancelConfirmedAt`을 분리한다

- `canceledAt` — 우리가 포인트를 회수하고 취소로 **기록한** 시각(①)
- `cancelConfirmedAt` — 토스 취소가 실제로 **확인된** 시각(③)

①을 커밋한 직후 서버가 죽으면 "우리는 취소, 토스는 승인" 상태가 남는다(포인트만 회수, 환불 없음).
프로세스 안의 보상으로는 닫을 수 없는 창이므로, 나중에 **식별할 수 있게** 두 시각을 나눠 남긴다.
`cancelConfirmedAt IS NULL`인 취소 주문이 곧 역방향 대사의 후보다(후속 PR).

### 5. 멱등 판정을 `isDone()`에서 `isSettled()`로 교체

취소가 생기면서 기존 멱등 판정이 조용히 깨진다. `settle()`은 "이미 DONE이면 no-op"이었는데,
취소된 주문은 `DONE`이 아니다 → **취소 후 뒤늦게 도착한 웹훅·대사가 환불한 포인트를 되살린다.**
적립 여부는 "DONE인가"가 아니라 **"READY를 벗어나 승인된 적이 있는가"**로 판정해야 한다
(`DONE | PARTIAL_CANCELED | CANCELED`). 상태를 추가할 때 기존 가드의 의미가 바뀌는 전형적인 함정.

### 6. 토스 멱등 키는 "이번 취소액"이 아니라 "누적 취소액"

우리 쪽 동시 취소는 DB 락이 막지만, **네트워크 재시도**는 못 막는다(토스가 처리한 뒤 응답 유실).
그래서 토스 `Idempotency-Key`를 함께 보낸다. 이때 키를 *이번 취소액*으로 만들면 같은 금액의
부분 취소를 두 번 할 때(1만원을 5천원씩) 키가 겹쳐 **토스가 첫 결과를 재생**한다 — 장부엔 1만원
취소로 남지만 실제로 돌아간 돈은 5천원인 조용한 손실이다. 누적 취소액은 단계마다 단조 증가하므로
유일하다.

### 7. `PointTransaction.REFUND` 신설

`DEDUCT` 재사용을 기각했다. 사용자가 좌석에 쓴 것과 환불로 되돌려진 것이 같은 타입이면 포인트
이력이 사실을 말하지 못한다. 보상(복구)은 별도 타입을 만들지 않고 `CHARGE`로 남긴다 — 실제로
잔액이 두 번 움직였으므로(회수 → 복구) 원장처럼 반대 거래를 추가하는 것이 맞다.

### 8. 인증은 BOOKER 본인 스코프

정책상 "관리자·수동"이지만 현재 역할 체계에 ADMIN이 없다. ADMIN 신설은 user/auth 도메인까지
번져 검증 단위가 둘로 갈리므로, 이번엔 **본인 주문만 취소 가능한 BOOKER 엔드포인트**로 두고
셀프 UI를 붙이지 않는 것으로 정책("고객 문의 경유")을 지킨다. 한계는 아래에 명시한다.

## 불변식 (구현 시 유지)

- **되돌릴 수 없는 호출은 항상 마지막에.** 외부 취소보다 앞에 오는 모든 변경은 되돌릴 수 있어야 한다.
- **취소 기록이 외부 호출보다 먼저 커밋된다.** 이 순서가 중복 취소를 막는 유일한 장치다.
- **환불액 ≤ min(주문 잔여액, 포인트 잔액).** 잔액을 음수로 만들지 않고, 주문액보다 많이 환불하지 않는다.
- **적립 멱등은 상태 집합으로 판정한다.** 취소 상태가 "미적립"으로 오인되면 안 된다(5번).
- **종결 상태 재전이 거부** — `READY`/`FAILED`/`EXPIRED`에서 취소로 가는 경로는 없다.

## 한계

- **포인트는 대체가능(fungible)해서 "이 주문의 미사용분"을 정확히 셀 수 없다.** 환불액을 현재 잔액으로
  근사하므로, 쿠폰으로 받은 잔액이 이 주문의 환불 재원이 될 수 있다. 정확히 하려면
  `PointTransaction ↔ PaymentOrder` 연결 + FIFO lot 추적이 필요하다(기존 백로그의 구조적 공백).
- **① 커밋 후 ② 호출 전 크래시 창이 남는다.** 포인트만 회수되고 환불은 안 된 상태.
  `cancelConfirmedAt IS NULL` 주문을 재시도하는 **역방향 대사가 후속 PR로 반드시 따라와야 한다** —
  이 ADR은 그 필요성을 만든 쪽이지 해소한 쪽이 아니다.
- **운영자가 사용자 대신 취소할 수 없다**(8번). ADMIN 역할 도입 시 확장 지점.
- **비동기 결제수단(가상계좌) 환불 경로는 여전히 없다** — 계좌 정보 수집이 필요해 성격이 다르다.
- **실 토스 취소 E2E 미검증.** 현재 주입된 키는 토스 공용 문서 테스트 키(`mId=tvivarepublica`)라
  개발자센터 '테스트 결제내역'이 계정에 묶이지 않아 역방향 실험이 제한된다. 본인 테스트 키 교체 후 확인.
- 취소 사유·감사 로그는 토스에 전달되는 문자열까지. 내부 감사 테이블은 없다.
