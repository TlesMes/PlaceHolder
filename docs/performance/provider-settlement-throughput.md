# 제공자 정산 적립의 처리량 상한 — 측정 계획 및 재설계안

> 상태: **계획 (측정 미실시)**
> 작성: 2026-08-21 (제공자 정산액 lost update 수정 세션)
> 관련: [ADR-020](../adr/ADR-020-point-bucket-separation.md), [ADR-008](../adr/ADR-008-lock-strategy.md),
> [정산 조회 무페이징 한계](./settlement-query-scalability.md), `loadtest/HANDOFF-D2.md`

## 한 줄 요지

제공자 정산액 lost update를 **비관적 락으로 막았다**(`b6f879d`). 정합성은 확보됐지만
**같은 제공자의 좌석 판매가 계정 행 하나에서 직렬화된다.** 이 상한이 실제로 문제가 되는지
측정하고, 문제라면 **정산 잔액을 원장에서 파생**시키는 방향으로 재설계한다.

**핵심은 순서다 — 지금 재설계하지 않는다.** 상한이 존재한다는 것과 그것이 병목이라는 것은
다른 주장이고, 후자는 아직 측정된 적이 없다.

## 1. 어쩌다 상한이 생겼나

### 고친 결함 (배경)

`settlementBalance += amount`가 락 없이 read-modify-write 되고 있었다. JPA 더티 체킹은
절대값(`SET settlement_balance = ?`)을 쓰므로, 서로 다른 예약자가 같은 제공자의 **다른** 좌석을
동시에 확정하면 적립이 서로 덮어써졌다. 좌석 락도(다른 행) 예약자 계정 락도(다른 행)
이들을 직렬화하지 못한다.

재현 결과(`ProviderSettlementConcurrencyTest`, 수정 전):

```
동시 확정 10건 → 전부 성공
SETTLE 이력    → 10행 (정상)
정산 잔액      → 5,000   ← 50,000이어야 한다. 9건 유실
```

**이력은 INSERT라 덮어쓸 것이 없고, 잔액은 UPDATE라 덮어써진다.** 같은 사실을 두 곳에
저장하면서 갱신 방식이 달라 갈라진 것이다.

### 수정과 그 대가

`findByUserIdForUpdate`를 추가하고 확정 경로가 이를 쓰도록 했다. 락 순서 규약은
**좌석 → 예약자 계정 → 제공자 계정**으로 확장됐다(제공자 계정을 잠그는 경로는 확정뿐이라
순환 대기 없음). 락 획득은 트랜잭션의 **가장 마지막**으로 옮겨 보유 구간을 최소화했다 —
락은 획득부터 커밋까지 유지되므로 "언제 잡느냐"가 곧 보유 시간이다.

**남은 것:** 인기 이벤트에서 한 제공자의 모든 확정이 그 한 행을 두고 줄 선다.
대기열(E-1)이 유입을 셰이핑해도 **확정 자체는 직렬화된다.**

## 2. 측정 계획

### 무엇을 증명해야 하나

1. 제공자 계정 락이 **실제로** 확정 처리량의 상한인가
2. 그 상한이 얼마인가 (초당 확정 수)
3. 상한의 원인이 **그 행**임을 어떻게 아는가

3번이 핵심이다. 숫자가 낮게 나와도 원인이 다른 데 있을 수 있다.

### 설계

| 항목 | 내용 |
|---|---|
| 부하 | 같은 제공자의 서로 다른 좌석을 동시 확정 (재현 테스트를 부하 규모로 확대) |
| 비교군 | ① 락 있음(현재) ② 파생(INSERT만, 프로토타입) |
| **대조 변수** | **제공자 수 1 → N.** 제공자를 늘렸을 때 처리량이 선형으로 오르면 병목이 그 행임이 증명된다 |
| 지표 | 초당 확정 수, confirm p95/p99, **제공자 계정 락 대기 시간** |

**대조 변수가 이 측정의 심장이다.** 제공자 1명일 때와 N명일 때를 비교하지 않으면
"느리다"는 관측만 남고 원인은 미지로 남는다 — D-2가 정확히 그렇게 끝났다.

### D-2의 교훈 적용

D-2(hold knee point)는 **부하생성기가 먼저 병목**이 되어 "서버 한계를 재지 못했다"로 끝났다.
coordinated omission 때문에 "안 죽는다"도 "죽는다"도 말할 수 없었다.

**이번은 유리하다.** 단일 행 경합은 인프라 처리량보다 **훨씬 낮은 부하에서** 드러난다.
생성기가 한계에 닿기 전에 꺾이므로 D-2의 함정을 피해 간다. 다만 같은 실수를 반복하지 않도록,
**꺾인 지점이 생성기 탓이 아님을 대조 변수(제공자 수)로 확인**해야 한다.

### 반대편도 재야 서사가 완결된다

파생으로 바꾸면 비용이 **쓰기 경합 → 읽기 누적**으로 이동한다. 그러니 재설계 후에는
정산 조회 응답을 **SETTLE 행 수를 늘려가며** 측정해 "상한을 없앤 대가"를 수치로 남긴다.
이 축은 [정산 조회 무페이징 한계](./settlement-query-scalability.md)와 자연스럽게 합쳐진다.

## 3. 재설계안 — 정산 잔액을 원장에서 파생

확정 트랜잭션은 `SETTLE` 행을 **INSERT만** 한다. 제공자 계정을 건드리지 않으니
경합이 **소멸**한다(상한을 올리는 게 아니라 없앤다).

이는 ADR-020이 예약자 측에 적용한 원칙을 제공자 측에도 적용하는 것이다:

> 버킷이 진실이고 `getBalance()`는 파생이다. 둘 다 저장하면 어느 한쪽만 갱신하는 코드가
> 생겨 진실이 갈라진다.

현재 제공자 쪽이 바로 그 "둘 다 저장해서 갈라졌던" 상태였다(위 재현 결과).

**전제 사실:** `settlementBalance`는 [ProviderAccountService](../../src/main/java/com/placeholder/domain/provider/service/ProviderAccountService.java)의
대시보드 응답에서만 읽힌다. **아무 판단도 이 값에 걸리지 않는다** — 검증도 게이트도 차감도 없다.
그래서 파생으로 바꿔도 실시간 정합성 요구가 없다.

### 무한 성장 문제와 해법

`SETTLE` 원장은 append-only라 SUM 대상이 계속 늘어난다. 표준 해법은 **스냅샷 + 증분**이다.

```
정산 잔액 = 스냅샷 잔액 + SUM(스냅샷 이후 SETTLE)
```

- `settlement_snapshots(provider_id, as_of, balance)`를 배치가 주기적으로 기록
- SUM 대상이 **스냅샷 주기 이내로 유계**가 된다 (일 단위면 최대 하루치)
- 스냅샷 기록은 배치라 확정 경로와 **경합하지 않는다**
- 배치 골격은 `PaymentReconciliationScheduler` 패턴 재사용 (cron + `zone=Asia/Seoul` 명시)
- 커버링 인덱스 `(user_id, type, amount)` 동반

**도메인상 더 자연스러운 유계 조건:** 정산예정액은 원래 **미지급분**이다. 정산 지급(`PAYOUT`)이
생기면 지급된 `SETTLE`은 합산 대상에서 빠져 자연히 유계가 된다. 지금은 지급이 미구현이라
(CLAUDE.md: "정산: 집계까지만, 현금 출금 없음") 무한히 쌓인다.
→ 이는 **ADR-020 갚을 신호 1번("제공자 측 거래 종류가 늘 때")과 같은 지점**이다.

## 4. 저장소 평가 — DB vs Redis

집계 전 증분을 어디에 담을 것인가에 대한 평가. **결론: 원장은 DB. 선택지가 아니다.**

### Redis를 원장 자리에 두면 안 되는 이유

| | 근거 |
|---|---|
| **이미 DB 적재 중** | `SETTLE` 행은 확정 트랜잭션 **안에서** 저장된다 — 좌석 CONFIRMED·예약 생성·포인트 차감과 원자적. 새로 만들 것이 아니라 이미 가진 것이다 |
| **dual write** | 커밋은 MySQL, 증분은 Redis → 커밋 성공 후 `INCRBY` 전에 죽으면 **좌석은 팔렸는데 정산이 없다.** 재시도로 수렴하지 않는다(원본이 없으므로) |
| **AOF는 돈의 유일한 기록이 되기엔 약하다** | `--appendonly yes`지만 fsync 기본이 `everysec` → 최대 1초 치 유실. 대기열 토큰이면 TTL 안전망으로 흡수되지만(ADR-013) 정산액은 재계산할 방법이 없다 |
| **ADR-013 원칙 반전** | 이 프로젝트는 "대기열 = 트래픽 셰이핑, 정합성은 DB"로 층을 나눠뒀다. Redis를 원장으로 쓰면 **돈의 정합성을 Redis에 맡기는 것**이라 그 구분이 무너진다 |

### Redis의 정당한 자리 — 읽기 캐시

거꾸로면 성립한다. **DB 원장이 진실, Redis는 계산된 SUM을 캐싱.**

- 확정 시 `INCRBY`로 캐시 갱신하되, 틀려도 **DB에서 재계산해 복구 가능**
- 캐시 미스·Redis 장애 → DB에서 SUM 재구성 (ADR-014 read-through 기조)
- **재구성 가능한 파생값**이라 유실이 손실이 아니다

**단 지금은 시기상조다** — 정산 조회가 느리다는 측정이 없다. PR #14에서 enter fast-path를
"시기상조"로 제거한 것과 같은 판단.

### 결론

| 층 | 저장소 | 이유 |
|---|---|---|
| 원장 (`SETTLE` 행) | **DB** | 확정 트랜잭션과 원자적. 유일한 진실 |
| 스냅샷 (주기 집계) | **DB** | 배치가 쓰므로 확정 경로와 무경합. 재계산 가능 |
| 읽기 캐시 | (측정 후) Redis | 재구성 가능한 파생값일 때만 |

## 5. 단계

1. ~~lost update 차단 (비관적 락)~~ — 완료 `b6f879d`
2. **측정** — 2절 설계대로. 제공자 수 대조 변수 필수. *인프라 의존(부하 환경)*
3. **판단** — 상한이 실제 병목이면 4단계, 아니면 여기서 종료하고 측정 결과만 문서화
4. **재설계** — `SETTLE` INSERT만 + 스냅샷 배치 + 커버링 인덱스. `settlement_balance` 컬럼 제거
5. **역방향 측정** — 정산 조회 응답 곡선(행 수 증가). settlement-query-scalability와 병합

## 6. 미결

- **측정 환경:** D-2처럼 앱·DB·부하생성기가 한 PC를 공유하면 해석이 흐려진다. 다만 단일 행
  경합은 낮은 부하에서 드러나므로 D-2보다 덜 민감할 것으로 본다 — **가정이며 확인 필요.**
- **스냅샷 주기:** 일 단위가 기본 후보. 실제 판매량을 보고 정한다.
- **`PAYOUT` 도입 시점:** 지급이 생기면 유계 조건이 도메인에서 자연히 나온다. 그때 4단계를
  함께 하는 것이 ADR-020이 말한 "갚을 시점"과 맞는다.
